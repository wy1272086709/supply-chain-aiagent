# Token 消耗实测报告：一次问答到底烧多少、烧在哪

> 日期：2026-10-25　|　对象：knowledge-hub `/ai/chat`（非流式问答链路）
> 数据：[results/token_report.md](results/token_report.md)（机器账单）｜方法脚本：[token_proxy.py](token_proxy.py) + [measure_tokens.py](measure_tokens.py)
>
> **一句话结论：一次问答平均 8,464 tokens、约 5 厘钱；大头不是大模型生成（12%），是重排 rerank（63%）——省钱先砍 rerank 的候选池，不是砍生成。**

---

## 一、为什么之前没有这个数

`/ai/chat` 的响应不透出 token usage，DashScope 也不提供按请求查询的账单接口——**链路上每次内部调用（改写、评估、重排、生成）都是黑盒**。分侧测评（[分侧测评方案与结果.md](分侧测评方案与结果.md)）把 token 成本列成了"已设计未实施"。

本报告把它做实了。方法不给应用改一行代码：**在应用和 DashScope 之间插一个透明计量代理**。

## 二、怎么测的

### 2.1 计量代理

```
应用 ──► 本地代理(:9090) ──► DashScope
              │
              └── 每次调用记录：时间戳 / 调用角色 / prompt_tokens / completion_tokens / total_tokens
```

- 应用按 OpenAI 兼容接口配置 base_url，把**生成、向量、重排**三路调用全部指向代理（三个环境变量，改配置不改代码）；
- 代理原样转发请求，从**响应体**里取 usage 记账，从**请求体**里识别调用角色；
- 计量失败不影响转发（代理对业务零侵入，测完摘掉即可还原）。

### 2.2 角色识别（不改代码怎么知道每次调用是干嘛的）

代理按请求特征给每次调用贴标签：

| 角色 | 识别方式 | 对应链路环节 |
| --- | --- | --- |
| router | 系统提示词前缀「意图与检索改写器」 | 意图分类 + 检索词改写 |
| grader | 「检索评估器」 | 切题评估闸门 |
| rewriter | 「检索改写器」 | 不切题时的二次改写 |
| generation | 「企业知识库助手」 | 最终答案生成 |
| embedding | 请求路径 `/embeddings` | 查询向量化 |
| rerank | 请求路径含 `rerank` | 候选块精排 |

### 2.3 归账：按调用序列，不按时间窗

每题跑 `/rag/search`（单独测检索）+ `/ai/chat`（完整问答）。问答链路的调用顺序是确定的：
`router → embedding → rerank → grader →（rewriter → embedding → rerank → grader）→ generation`。
归账按**调用序列模式**分段：以 generation 结尾切段，段内 router 之前的 emb+rerank 对属于检索窗口。

> 踩坑记录：第一版按客户端时间窗归账，窗口边界处把检索的 rerank 错记进了相邻问答窗口（数字虚高 60%）。改成按序列模式后，逐条对账 215,392/215,392 tokens 无漏记、无重复。**教训：异步链路的成本归账，用确定性序列模式，别用时间窗。**

### 2.4 抽样

15 题 16 个问答行（含一组多轮链），覆盖全部题型 L1~L6、两道摇摆题、一道拒答题。共 115 次模型调用。

## 三、实测结果

### 3.1 单题账单（/ai/chat 一次完整问答）

| 角色 | 均值 tokens/题 | 占比 | 说明 |
| --- | --- | --- | --- |
| **rerank** | **5,328** | **63%** | 1~2 次调用；RRF 融合后的 **top-20 候选块**整批送精排 |
| grader | 1,149 | 14% | 切题评估：读 5 块 × 500 字摘录 |
| generation | 991 | 12% | 输入 909 / 输出 83——生成本身很省 |
| router | 861 | 10% | 意图分类 + 改写（结构化输出） |
| rewriter | 48（均摊） | <1% | 仅不切题时触发（16 行里 1 次） |
| embedding | 13 | ~0% | 查询向量化，可忽略 |
| **合计** | **8,464** | 100% | 中位数 8,353，最大 12,927 |

**关键事实：直觉以为"大模型生成最烧钱"，实测它只占 12%。真正的成本大头是 rerank——把 20 个候选块（每块最多 2000 字）送进重排接口，一次就 5,000+ tokens，比整条 LLM 判断链还贵。**

### 3.2 按题型

| 题型 | 均值 tokens/题 | 备注 |
| --- | --- | --- |
| L1~L4、L6 | 7,700 ~ 8,700 | 差异不大：上下文长度随题型略增 |
| **L5 边界拒答** | **12,927（+53%）** | 最贵：检索→评估不切题→改写→**二次检索**→再评估→拒答生成。走满两轮循环——这是"宁可多查不编造"的设计代价，贵得值 |

检索单独调用（/rag/search）：均值 5,331 tokens（embedding 17 + rerank 5,314）——与问答内部的检索成本一致，印证 rerank 是检索侧的固定开销。

## 四、换算成钱

价格依据（2026-10 阿里云百炼官网，[模型定价页](https://help.aliyun.com/zh/model-studio/model-pricing)、[text-embedding-v3](https://help.aliyun.com/zh/model-studio/text-embedding-v3)；以实际账单为准）：

| 服务 | 单价 |
| --- | --- |
| qwen-plus 输入 / 输出（非思考，≤128K 档） | ¥0.8 / ¥2 每百万 |
| qwen-plus 输出（思考模式） | ¥8 每百万（本链路未启用） |
| text-embedding-v3 | ¥0.5 每百万 |
| rerank（qwen3-rerank 档） | 按 ¥0.5 每百万估 |

**单题成本 ≈ ¥0.0053（5 厘钱）**：LLM 部分 ¥0.0026（2,806 进 + 198 出）+ rerank ¥0.0027 + embedding 忽略不计。

| 规模 | tokens/天 | 成本 |
| --- | --- | --- |
| 100 题/天 | 0.85M | ¥0.5/天（¥15/月） |
| 1,000 题/天 | 8.5M | ¥5.3/天（¥160/月） |
| **3,000 题/天（客户"一天几千次"）** | 25M | **¥16/天（¥480/月）** |
| 10,000 题/天 | 85M | ¥53/天（¥1,590/月） |

对照业务价值：一题 7 秒、省约 4 分钟人工翻档。3,000 题/天 = 每天省 200 人时，花 ¥16 模型费。**这套架构里 token 不是瓶颈，人才是。**

（附带：全量跑一遍 56 行考卷 ≈ 采集 ¥0.44 + 判卷 ¥0.23 ≈ **¥0.7**——与前作"全量成本 <1 元"的预估吻合。）

## 五、哪里能省（按实测占比排序，附风险与验证法）

| 优先级 | 动作 | 预估节省 | 风险 | 怎么验证 |
| --- | --- | --- | --- | --- |
| ① | **rerank 候选 20→10**（`RAG_HYBRID_TOP_K`） | 总成本 -30%（rerank 减半） | 排 11~20 的相关块漏精排——但块精确率实测 @K=45%，后段本就多是噪声，预期无损 | 跑 48 题回归：Hit@3 / MRR / 准确率不掉即成立 |
| ② | **判断链换轻量模型**（router/grader 用 turbo/flash 档） | LLM 部分 -70%（占总成本 24%→7%） | 路由/评估准确率可能降——历史上路由误判造成过 R3 那轮 31% 的事故 | 回归 + 单独对比 router 判定一致率 |
| ③ | **热门问题缓存**（query→hits LRU） | 重复查询的检索成本→0 | 缓存失效策略（文档更新要击穿） | 统计真实 query 重复率再决定 |
| ④ | 生成上下文 5 块→3 块 | -8% 左右 | 多跳题需要多块（L4 实测上下文最长） | 分题型回归，L4 单独看 |
| 不该省 | L5 的两轮循环、grader 闸门 | — | 省了它们 = 拿幻觉率换钱 | — |

**砍的顺序和占比严格对应**：先砍 63% 的大头（rerank 候选池），再砍 24%（判断链降档），最后才是 12% 的生成。反过来砍（先换小模型生成）是省了零头、丢了答案质量。

## 六、局限（如实）

1. **实测的是非流式 `/ai/chat`**。流式 Agent 路径（`agent.py`：多轮工具调用 + 思考模式输出 ¥8/M）未计量——按结构推断会是数倍成本，那才是"Agent 转圈烧 token"的主战场，是下一个要测的对象。
2. 抽样 16 行，L5 仅 1 题（拒答路径的 +53% 是单样本）；量级可信，比例待扩样。
3. rerank 单价按同档 ¥0.5/M 估（8/31 起 VL-Rerank 降至 ¥0.5），以账单为准。
4. 未含**写路径**成本：文档发布时的图谱抽取（每块一次 LLM 调用）是入库时的钱，查询侧不重复花——量级取决于文档量，另测。
5. 思考模式输出价差 4 倍（¥2→¥8）——将来若给生成开思考，只影响 12% 里输出那小部分，账仍然清楚。

## 七、复现

```bash
# 1) 起计量代理（自动清空上次日志）
uv run python evaluation/token_proxy.py &
# 2) 用指向代理的环境变量重启应用
OPENAI_BASE_URL=http://127.0.0.1:9090/compatible-mode/v1 \
EMBEDDING_BASE_URL=http://127.0.0.1:9090/compatible-mode/v1 \
RERANK_BASE_URL=http://127.0.0.1:9090 \
uv run uvicorn app.main:app --port 3000 &
# 3) 抽样采集 + 出账单
cd evaluation && BASE_URL=http://127.0.0.1:3000 uv run python measure_tokens.py
# 只重算不重采：uv run python measure_tokens.py --aggregate-only
```
