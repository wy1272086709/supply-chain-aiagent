# 知识库（RAG）测评方案

> 场景：访谈客服、结算、运营三类岗位，梳理《理赔 SOP》《运费合同结算手册》《站点操作手册》，构建知识库问答系统后，需要量化评估效果。
>
> 本方案回答三个问题：**测什么（指标）、拿什么测（测试集）、怎么测（步骤）**，并提供全套可执行脚本。
>
> **v2 升级**：在本文端到端指标之上，新增检索侧（块级上下文精确率、信息点召回）、生成侧（忠实度、误拒率）、溯源侧（引用正确性）、稳定性（重复运行）与多轮题型（L6）——设计、口径与实测见 [分侧测评方案与结果.md](分侧测评方案与结果.md)，测试集用 [golden_set_v2.jsonl](golden_set_v2.jsonl)。

---

## 一、背景与目标

| 项 | 说明 |
| --- | --- |
| 测评对象 | knowledge-hub 的 RAG 问答链路：`/rag/search`（BM25+kNN→RRF→rerank）与 `/ai/chat`（检索→生成→引用） |
| 知识语料 | 三份岗位操作手册（`manuals/` 目录，当前为**合成演示版**，后续替换为访谈产出的真实文档） |
| 测评目的 | ① 证明系统可用性（准确率/命中率）② 量化效率收益（节省查文档时间）③ 暴露优化点（错在哪类题、检索没找到还是答错） |

**重要**：当前 `manuals/` 下三份手册是为了打通测评流程而合成的演示稿（华驿物流虚构数据）。访谈完成后，把真实 SOP/合同/手册按同样结构替换进去，并同步修订 `golden_set.jsonl` 的标准答案与出处。

## 二、指标体系（测什么）

### 2.1 检索质量（测 `/rag/search`）

| 指标 | 公式 | 说明 |
| --- | --- | --- |
| **检索命中率 Hit@K** | 出处文档出现在召回前 K 条的题数 ÷ 可检索题数 | 主指标，K=3（业务上用户只看前几条） |
| MRR | mean(1 / 标准出处文档首次命中排名) | 衡量"排得靠不靠前"，1.0 = 全部第 1 |

- 判定粒度：**文档级**（标准出处文档的标题出现在召回结果 `documentTitle` 中即算命中）。L5 边界题无出处，不计入。
- 检索指标全自动计算，无需 LLM。

### 2.2 回答质量（测 `/ai/chat`）

| 指标 | 定义 | 判定方式 |
| --- | --- | --- |
| **回答准确率** | 评审得分≥阈值（默认"完全正确"）的题数 ÷ 有效作答题数 | **LLM 评审为主**（qwen-plus 按 0/1/2 打分，数字必须与标准答案完全一致）+ 人工抽检 20% 校准；无 Key 时退化为关键词覆盖率≥60% |
| 边界拒答正确率 | L5 题中正确说明"知识库未覆盖且未编造"的比例 | 同上 |
| **幻觉率** | 1 − 拒答正确率（L5 题编造数字/规则的比例） | 同上 |

**为什么要分层型**：准确率一个总数会掩盖问题。L1 错=知识没进库；L3 计算错=prompt/模型推理弱；L5 编造=拒答策略没做。分岗位、分题型看才能定位优化点。

### 2.3 效率收益（业务价值指标）

| 指标 | 公式 | 说明 |
| --- | --- | --- |
| 平均响应耗时 | mean(/ai/chat 端到端秒数) | 客户端计时，含检索+生成 |
| **单题节省时间** | 人工查文档基线秒数 − AI 耗时秒数 | 基线优先用**实测**（见 §5），无实测时用分题型默认估计：L1=180s、L2=300s、L3=420s、L4=480s、L5=240s |
| **节省率** | Σ节省时间 ÷ Σ人工基线 | 报告中必须注明基线来源（实测/估计） |

> 诚实性提醒：用估计基线得出的"节省时间"只能作为方向性参考，对外汇报请标注口径；实测方法见 §5。

## 三、测试集设计（拿什么测）

`golden_set.jsonl`：**48 题 = 3 岗位 × 16 题**，每题含标准答案、答案关键词、出处文档/章节、人工基线估计。

| 题型 | 每岗位题量 | 考什么 | 示例 |
| --- | --- | --- | --- |
| L1 事实 | 5 | 单点数字/清单查找 | "客户签收后发现破损最晚多久报案？"→48 小时 |
| L2 规则判断 | 4 | 规则分支匹配（最常出错的业务场景） | "签收第 3 天才报短少怎么定性？"→拒赔 |
| L3 计算 | 3 | 多规则组合计算 | "45 元运费未保价全丢赔多少？"→135 元 |
| L4 多跳 | 2 | 跨章节/跨表格组合 | "赔多少+谁审批+多久出结果" |
| L5 边界拒答 | 2 | 知识库外问题（防幻觉） | "理赔年度预算？"→应明确拒答 |

设计原则：
1. **问题口语化改写，不照抄原文措辞**（考语义检索，不是字符串匹配）；
2. 每个关键数字至少被 1 题覆盖，高频易错点（拒赔、进位、档位边界）重点布题；
3. L5 故意问库外问题，专测"不懂装懂"；
4. 标准答案全部可追溯到手册章节，答案先行、有据可查。

## 四、执行步骤（怎么测）

### Step 0　准备环境

```bash
# 1) .env 设置并重启应用
DOCUMENT_REQUIRE_APPROVAL=false      # 免审直接发布
DASHSCOPE_API_KEY=sk-xxx             # 对话与评审都需要
# 2) 启动依赖栈（PG/Mongo/Redis/RabbitMQ/ES）与应用（:3000）
# 3) 预置账号 user/123456（权限：document:create、search）
```

### Step 1　导入语料并等索引就绪

```bash
cd evaluation
python upload_manuals.py            # 发布 3 份手册 + 轮询探针直到可检索（最长 180s/篇）
```

### Step 2　（可与 Step 3 并行）采集人工基线

见 §5。若暂无人力，直接用默认估计，报告注明。

### Step 3　批量采集（检索 + 问答 + 耗时）

```bash
python run_eval.py                  # 全量 48 题 → results/raw_results.jsonl
# 冒烟：python run_eval.py --only CS-L1-01,ST-L3-01,OP-L5-01
# 只测检索（无 LLM Key）：python run_eval.py --skip-chat
```

### Step 4　评审 + 出报告

```bash
DASHSCOPE_API_KEY=sk-xxx python judge_and_report.py
# 带实测基线：python judge_and_report.py --baseline baseline_filled.csv
```

产出 `results/report.md`（总览/分岗位/分题型/失败案例清单）与 `results/judged.jsonl`（逐题明细）。

### Step 5　人工抽检（不可省）

- 从 judged.jsonl 按**分层抽样 20%（约 10 题）**人工核对 LLM 评审结论；
- 评审与人工不一致 ≥3 题 → 校准评审 prompt（更严/更宽）后重跑 Step 4；
- 抽检记录（题号、一致与否）附进最终文档。

### Step 6　写报告

以 `results/report.md` 为骨架，补上 §6 模板的"结论与改进建议"，即成对外交付的测评文档。

## 五、人工基线采集方法（节省时间指标的口径）

**目的**：得到"没有 AI 时，员工翻文档回答同一批题要多久"的真实秒数。

1. 招募每岗位 1~2 名在职员工（合计 3~6 人）；
2. 从对应岗位 16 题中抽 8~10 题（覆盖各题型），提供该岗位手册（纸质/PDF 均按真实工作形态）；
3. 模拟真实查档：计时从读题到给出含关键数字的完整答案为止，允许翻文档不允许问人；
4. 每题由 ≥2 人作答，取**中位数**填入 `baseline_template.csv` 的 `seconds` 列；
5. 同时记录员工对 AI 答案的可采信度评分（1-5），作为准确率的人工佐证。

成本约每人 40 分钟；拿不到人力时退回估计基线（报告标注"估计口径"）。

## 六、报告模板（对外交付结构）

```markdown
# 知识库问答测评报告（客服/结算/运营 三岗位）
## 1. 测评结论（TL;DR：准确率 xx%、命中率 xx%、平均节省 xx 分钟/题）
## 2. 测评设置（语料、题量、评审方式、基线口径、topK、日期）
## 3. 总体指标表（命中率 Hit@3 / MRR / 准确率 / 幻觉率 / 平均耗时 / 节省率）
## 4. 分岗位 × 分题型明细表
## 5. 错误分析（检索未命中 vs 命中但答错 vs 编造；典型失败案例 3~5 个）
## 6. 业务价值测算（月均查询次数 × 单题节省 → 月度节省人时；口径注明）
## 7. 改进建议与下轮回归计划
```

业务价值测算示例：若客服组日均知识查询 50 次、单题平均节省 4 分钟 → 月度节省 ≈ 50×4×22÷60 ≈ 73 人时。

## 七、常见坑与注意事项

| 坑 | 对策 |
| --- | --- |
| 发布后立刻搜索搜不到 | 索引链路（MQ→分块→向量→ES）是异步的，`upload_manuals.py` 已内置探针轮询，勿省略 |
| 多题共用 sessionId | 历史轮次会污染检索改写，`run_eval.py` 每题独立会话 |
| LLM 评审过宽 | prompt 已要求"数字完全一致才给 2 分"；抽检不一致率高就收紧并重跑 |
| 计算题判定争议 | L3 的关键词就是最终数字（如 135/2580/5527.4），评审只认数字对不对 |
| topK 影响 | 报告固定记录本次 topK；调参对比时只改 topK 并另存一份 results |
| 重复运行 | `upload_manuals.py` 重复跑会产生同名重复文档，先在管理端删除旧文档再导 |
| 费用 | 全量 48 题 ≈ 48 次检索 + 48 次生成 + 48 次评审，qwen 系模型成本可忽略（<1 元量级） |

## 附：三岗位访谈提纲（用于产出真实版手册）

**客服（理赔 SOP）**：近一个月典型理赔工单走一遍｜报案到结案的每步时限与负责人｜保价/未保价/国际件赔付标准表｜拒赔最常见的 3 种争执及口径｜审批权限金额分档｜系统与线下材料的差异。

**结算（运费合同）**：一张真实账单从出账到回款的完整流程｜计费重进位与附加费清单（含当月系数）｜对账差异 TOP3 类型与处理 SOP｜返点/最低消费等合同条款模板｜发票税率与开票节奏。

**运营（站点操作）**：跟班一天记录到件→上架→派送全链路｜异常件（破损/拒收/滞留）处置与升级路径｜盘点频率、差异率红线｜设备点检清单｜禁运品现场处置案例。
